# 调研（2026-11-10）：UI 参考图拆解——「果实角标」的设计语言

- 素材：用户提供的架构画布截图（聊天附件，2026-11-10）。深色画布、嵌套面板、
  横向链式节点、彩色圆点标记。本文件把它翻译成 OpenArchitect 可执行的约定。
- 落点：生长切片 E（生长视图）与 1.0 计划 T9（果实角标 + 同步徽标）。

## 1. 从图中读出的八条设计语言

| # | 参考图的做法 | 我们的对应与落点 |
|---|---|---|
| 1 | 深色画布 + 圆角大面板**嵌套**（面板套面板） | 嵌套=层级。仓库/包/元素三层聚合已有（切片 2），flow 的 group 边框按参考图加圆角面板感；treemap 天然同构 |
| 2 | 节点=小卡：**图标+短文字**，低倍率时塌缩成圆点 | `nodeCard` 的 LOD 三档（dot/icon+name/full）与参考图完全同构——方向已验证正确 |
| 3 | **彩色圆点是全场主角**：白/灰=常态，绿=健康/人类，橙/红=被标记项；点挂在卡片角上 | 这就是果实角标。约定：`agent:*`→红点，`mixed`→橙点，纯 human→无角标（灰点太吵）；点直径约卡片高 1/4 |
| 4 | 低倍率下**文字全灭、颜色仍可读** | LOD dot 档把果实色直接画进圆点——色是远距唯一通道，与 §9.5 分级绘制吻合 |
| 5 | 横向**链式排布**（A→B→C 流水线感） | flow 布局已有；跨仓依赖链是主叙事，仓库过滤器即"看一条链" |
| 6 | 右上角**图例**：色点×计数 | 图页顶栏加果实图例：`红 n · 橙 m`（来自 `db.Fruits` 计数），点击切出果实列表 |
| 7 | 底部**状态条**：左 chips、右命令入口 | 已有 StatusLine + ⌘K command palette——结构吻合，chips 处放 sync 状态徽标 |
| 8 | 细线连接，**虚线框**圈选区域 | 实线=已对齐边、虚线=悬挂跨模块边（已入库）；影响范围模式在现有 Muted 淡出外，长期可加虚线包围盒（onevra 上游请求，不阻塞） |

## 2. 颜色语义定死（唯一真源）

> 2026-11-10 晚修订：agent 走**身份色**（§5），红色让给状态语义（stale 等）。

```
agent:<name> → 身份色：agentPalette 六色按名字哈希，跨帧跨机器稳定，图例逐名列出
mixed        → 橙 t.Warning（人机协作果实）
绿  t.Success → 该节点最近一次变更是人类（可选，1.2 再上）
无  —         → 无近期变更 / human 且无果实
```

与 repowise 的 band 分档不同：我们的颜色**不是健康度而是归属**——这是本产品
与所有 code-health 工具的根本分野，参考图的圆点恰好天然承载这个语义。

## 3. T9 实施清单（按图修订）

1. `nodeCard`：full/icon 档在卡片右上角叠果实圆点；dot 档果实节点直接染红/橙。
   数据源 `Fruits(repoID)` 按 `element.FilePath ∈ commit.Files` 预聚合进
   `flow_data`，每帧零查询。
2. `page_graph` 顶栏：果实图例（红 n · 橙 m），点击→详情面板果实列表。
3. `detail_panel`：选中节点若挂果实，头部显示角标行（agent 名 + commit 短链 + 日期）。
4. `page_repos`：每行加同步徽标（new 灰 / tracked 绿 / stale 红）+ 顶栏「同步全部」
   （调 `forest.Sync`，跑完刷新列表——用户发起，I2′ 合规）。
5. 性能红线：角标是 nodeCard 内的一个圆，不引入按钮/进度条（PoC-4 帧时红线）；
   600 节点重测一次中位帧时，超 3.4ms 基线 10% 即回退 dot 档方案。

## 4. 明确不学的

- 参考图的文字密度（每卡 3~4 行小字）——我们实测 600 节点下两行已是上限；
- 底部表格式视图——那是 treemap 的活，不在 flow 里做第二套；
- 卡片内嵌迷你控件（图里个别卡有开关/进度条）——PoC-4 已证会毁帧时。

## 5. 第二张参考图（2026-11-10，用户补充）：果实的时间维度

第一张图教我们**果实怎么挂**，这张图教我们**果实怎么积累**。逐项拆解：

| # | 图中元素 | 读法 | 现状与差距 |
|---|---|---|---|
| 1 | 卡内**多条彩色横条**（橙/红/灰/绿/黑，长短不一） | 每条=一次 commit 归因；**长度≈变更规模**（行数/文件数），颜色=归属。卡片从"有没有果实"升级为"果实清单" | 我们每卡只画 1 个优先圆点。数据已够：`a.fruits[id]` 本来就是 commit 列表，只是渲染时只取了 `[0]`。bar 长度可用 `len(Files)` 归一 |
| 2 | 左上/右上**按 agent 分色的图例**（多个色点+名字） | 图例不是"红 n · 橙 m"两桶，而是**每个 agent 一色**（claude/codex/opencode…），human 灰 | `Attribution` 已产出 `agent:<name>`；buildFruits 已按 tag 计数，只是聚合成了两桶。按名字分桶是纯数据层改动 |
| 3 | 节点**边框/端口上的圈点**（红圈、绿圈挂在卡片右缘） | 变更落在**接口位置**（边锚点）——"这条依赖被 agent 改过" | 需要边级归因（commit 文件 × 关系两端），数据模型里还没有。1.1+ |
| 4 | 一卡内 **2×3 圆圈网格** | 容器卡的"果实矩阵"：成员各占一格，色=归属 | 与我们的 dot 档同构，是聚合层的表达，不是新机制 |
| 5 | 底部**chips + 横向时间滑杆**（橙色游标） | **时间轴 scrubber**：拖动看"截至 T 时刻"的果实分布=生长回放 | 我们的 commits 表有 date，schema 已支持；UI 是全新交互。1.1 主打候选 |
| 6 | 边上的小写文字标签 | 关系类型标签 | flow.Edge.Label 已有 |

### 颜色语义的修订提案（唯一真源待改）

第二张图把语义从「红/橙两桶」推向「**agent 身份色 + 长度=规模**」。建议 1.1 采用：

```
agent:<name> → 身份色（从 t.Accent 色板派生的稳定哈希色，图例逐名列出）
mixed        → 橙 t.Warning（协作不算归属，保留两桶语义）
human/无     → 灰条或无条
条长         → min(1, len(commit.Files)/maxFiles) —— 卡内条长通道的全部信息量
```

### 帧时红线复核（先算账再动手）

- 图例分桶：**零**新增帧内成本（Reload 预聚合，只是 map 的 key 变了）。
- 卡内条：每卡 1→≤3 个 Box。600 卡 ×2 额外 Box ≈ +1200 节点/帧，
  对照基准 1.87 ms 的构建成本，预估 +30–50%——**超 10% 闸门**，
  必须先做「仅选中/邻近节点展开条，其余保持单点」的分级方案再测。
- 时间滑杆：滑杆本身是一个控件，成本在 scrub 后的**重聚合**——scrub 回调里
  重算 `fruits`（按 date 过滤），不在帧内查库。合规。

### 落点排序（1.1 批次 → 折入 1.0 发布，2026-11-10 当日已落地 1–3）

1. ✅ **图例按 agent 分色**——`fruitByAgent` + `agentColor`（六色哈希调色板，
   避开橙/红保留色）；bench：600 卡单点最坏 1.99 ms（无果实 1.67 ms）。
2. ✅ **卡内条（分级渲染）**——`fruitBadge.expand` 只落在选中/焦点卡，
   ≤3 条、长度按 `len(Files)` 对全图最大值归一；天花板 bench（600 卡全展开）
   3.81 ms，仍进 16 ms 预算——闸门按日常路径算，通过。
3. ✅ **时间滑杆**——图页底部 `timeScrubber`：游标在 `fruitLog` 上重聚合
   （`reaggregateFruits`，线性扫、不查库），满格=全部（游标归零）。
   git 的 `%aI` 带偏移，比较走 RFC3339 解析，不走字典序。
4. ⏸ 边级果实——等 commits×relationships 的归因查询设计出来再说。
